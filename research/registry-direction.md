# Registry direction and reconciliation — 2026-09-04

## Responsibility

Pollen defines packaging, publishing, installation, runtime behavior, and robot safety. Hugging Face hosts weights and model cards. uDuck owns discovery, editorial context, immutable artifact references, and reproducible diagnostic observations. We should not invent a competing runtime contract or claim our simulator is the training environment.

Read the complete supplied 1,650-line conversation and GitHub issue [#17](https://github.com/ob1-s/uduck-registry/issues/17). The useful direction is pointer + curation, manifest ingestion, URL submission, and evidence outside source history. Several implementation claims in that conversation need correction:

- [Pollen's manifest](https://github.com/pollen-robotics/microduck/blob/main/docs/policy-manifest.md) explicitly makes fields optional. Missing fields are not compatibility evidence. Schema 2 by itself proves neither origin nor a baked normalizer.
- A constant encoding describes how the daemon feeds a command, not which command activates a behavior. Flamingo is a concrete counterexample: `[flag, side, 0]`. Do not infer a velocity sweep or an all-zero successful behavior from its `kind`.
- [The current robot cheatsheet](https://github.com/pollen-robotics/microduck/blob/main/docs/robot/cheatsheet.md) supports raw local files, manifest-less repositories, explicit files in repositories, `@revision`, and held-pose commands. “Not a schema-2 single-policy package” does not mean “impossible to install with robotctl.” Our automated admission policy is intentionally narrower than upstream's runtime.
- Manifest validity and ONNX shape checks cannot justify automatic behavioral certification or hardware verification. The legacy runner uses position-control diagnostics, not the publisher's BAM training environment.
- GitHub-token PRs may leave PR workflows pending approval. [Explicit workflow dispatch](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) runs CI for the bot branch. No imaginary `gh issue create -f url=...` interface is used.
- Native ONNX parsing/inference belongs in a job without write credentials. The PR-writing job only validates inert pointer data.

## Implemented model

- `registry/policies/*.json`: immutable repo revision and hashes plus curation and author media. No editable verification, command recipe, or copied runtime fields.
- `.generated/policies`: resolved upstream facts, generated by the shared Python resolver. The TypeScript CLI and issue ingestion use that resolver. Builds re-fetch pinned bytes and fail on hash mismatch.
- `/policies.json` and `/policies/<id>` expose resolved packages. The first migration is Flamingo, retaining `/behaviors/flamingo-cycle` and its per-entry API URL.
- `registry/behaviors`: explicitly legacy/manual descriptors. Existing entries remain visible. Upstream-shipped entries no longer claim independent registry hardware verification.
- `public/registry.json` is generated; README no longer embeds a generated table. New generated media is not source state.
- CI executes existing diagnostics before a build, binds reports to complete inputs, copies current results into the static deployment, and archives main results outside source history using GitHub Releases. Failed checks stay visible; rejected or failed execution stops that build.
- URL form → read-only native inspection → inert pointer validation in a separate write job → PR → explicit CI dispatch → maintainer review. This does not silently auto-merge untested physical behavior.

## Deliberate coverage limits

The new package path reports ONNX inspection separately from behavioral simulation. Generic activation/return-to-standing/held-pose recipes cannot be inferred soundly from the current manifest: numeric activation commands, accessory requirements, and simulator dynamics are not fully machine-readable. Such packages remain discoverable with “not covered”; they are not rejected merely for lacking our test coverage. Existing explicit diagnostic recipes keep working.

Evidence archives are durable per-main-commit releases; reports also carry a content-derived evidence key. No public CDN/bucket setup is required. There is no cross-build evidence cache yet: rerunning avoids promoting untrusted PR outputs. The source tree's existing author-media cache is retained; this change makes no geographical delivery promise.

Nightly discovery, a new simulator/BAM integration, automatic merge policy, contributor identity verification, and upstream machine-readable activation extensions are future product decisions, not prerequisites hidden behind “submit a URL.” GitHub repository settings must allow Actions to create PRs. Cloudflare deployment still uses the existing configured credentials. Runtime installation remains upstream-owned.

## Activation check

The latter Actions setting disables the bot PR-creation capability; it needs to be enabled before the issue bot can open PRs. Default workflow permissions should remain read-only.
